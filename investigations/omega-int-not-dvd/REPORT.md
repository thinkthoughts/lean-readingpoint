## 2. Mechanism (unchanged from round 1)

`omega` keeps disjunctions aside and splits them, last-in first-out, only after the linear problem
survives without them. For literal `k`:

* The `k = 0` branch is refuted at once, so the direct cost is one extra elimination plus an `Or.elim`.
* When `¬ k ∣ x` precedes other disjunction sources (`y ≠ c`, a `≠`/`=` goal), those are split first,
  and the needed fact appears only at the leaves. The result is **2^(r+1) − 1 case splits for r
  unrelated `≠` hypotheses**.

Minimal reproducers: `harness/tests/omega_int_not_dvd_perf.lean` and the two examples in `ISSUE.md`.

## 3. The preferred candidate L, and its comparison E

Both add one lemma to `Init/Omega/Int.lean`:

```lean
theorem emod_pos_of_not_dvd_of_bne {a b : Int} (w : (a != 0) = true) (h : ¬ a ∣ b) :
    0 < b % a :=
  (Int.emod_pos_of_not_dvd h).resolve_left fun h0 => by simp [h0] at w
```

The side condition is closed by `Eq.refl true`, which the kernel evaluates. A literal counts as
nonzero when `groundInt? k` (omega's existing evaluator) returns a nonzero value.

* **E:** `pushNot` returns `0 < x % k` directly.
* **L:** `addFact` routes `0 < x % k` to a new `MetaProblem.pending` list (trace: `deferring fact`).
  `omegaImpl` adds the pending facts once the problem survives without them, before calling
  `splitDisjunction` (trace: `adding N deferred facts`). Round 2 adds these two trace lines to the
  patch; everything else in L is unchanged from round 1.

### 3.1 The deferred-fact mechanism cannot regenerate itself (task 3)

**Structural argument (verified by reading `lazy.patch`).**
1. Only the `Not P` branch of `addFact` defers. It defers exactly when `notDvdLit?` matches
   `P ≡ (k : Int) ∣ x` with `groundInt? k ≠ 0`.
2. The deferred proof has type `0 < x % k`, an `LT.lt` application. When it is processed, `addFact`
   takes the `LT.lt` branch (`Int.add_one_le_of_lt`) and never re-enters `Not`. So a derived fact is
   never deferred again.
3. Pending facts are flushed with `pending := []` and processed by the ordinary `processFacts`. Each
   flush therefore strictly empties the list, and each `omegaImpl` call flushes at most once before
   it either finds a contradiction or splits.
4. `splitDisjunction` runs only when `pending` is empty. Branches inherit the empty list, and a
   `¬ k ∣ x` that appears inside a branch (`¬ 3 ∣ x ∨ …`, `¬ (3 ∣ x ∧ …)`) is deferred and flushed
   within that branch.

**Dynamic check (verified).** `gen/check_pending.py` replays every L trace (41 workloads) and checks
five properties:

* **D1:** only `¬ …` facts are deferred.
* **D2:** a flush of N facts empties exactly the N facts deferred in that round.
* **D3:** nothing is pending at a case split or at entry to a branch.
* **D4:** processing flushed facts defers nothing new.
* **D5:** every flushed fact is then processed, unless an earlier one already made the problem
  infeasible and the round ends in a contradiction.

All five hold, with totals of 109 deferred facts, 32 flushes, and 29 deferred facts left unused
because the problem was refuted first. A self-test feeds the checker one valid and three invalid
synthetic traces (re-deferral, a split with facts pending, a wrong flush count) and confirms it
rejects the invalid ones. B and E traces contain no deferrals.

## 5. `run.sh` contract (task 2)

`harness/run.sh` exits **0 only if every outcome matches its expectation**, and **1** otherwise. Each
check prints `ok` or `UNEXPECTED`, and `results/summary.txt` keeps the log. Checked expectations:

1. The patches apply, the lemmas in E and L are identical, and the build succeeds.
2. B reproduces the builtin tactic's case-split count on all 41 workloads.
3. Every test file gives the outcome in the table above. An expected failure must fail with the
   stated message and the stated number of errors. For the builtin tactic and B, the perf guard must
   fail with exactly one error, the heartbeat timeout.
4. Lean's `tests/elab/omega.lean`, `omega_examples.lean` and `omegaCanon.lean` (215 `omega` calls)
   pass on B and produce identical output on E, L and `omega_gi`.
5. D1–D5 hold for L, and B and E show no deferral.
6. Both benchmark runs complete for every workload, and heartbeats are identical between them.

`QUICK=1` skips 2, 5 and 6. `gen/fault_injection.sh` breaks two expectations in a copy (it raises
the guard limit so the baseline's expected failure disappears, and it breaks one correctness
example). It **verified** exit status 1 with 7 `UNEXPECTED` lines (`results/fault_injection.log`).
The final full run gave `ALL RESULTS AS EXPECTED`, exit 0, with 42 `ok` lines.

## 8. New, separate finding: `groundNat?` on an `Int` modulus

While writing the negative-literal tests, `omega` failed on
`example (x : Int) (h : x % (0 - 3) = 1) : x % (0 - 3) < 5 := by omega` with an internal
**`Application type mismatch`** error instead of a proof. Cause, verified by reading the code and by
the follow-up prototype: the `HMod.hMod` case of `asLinearComboImpl` evaluates the `Int` modulus with
`groundNat?`, so `0 - 3` becomes `0` and `x % (0 - 3)` is rewritten with `Int.emod_def x 0`.

* Same cause: `x % (2 - 3 + 4)` is read as `x % 4`, and `x % (-3)` stays an atom (`groundNat?`
  rejects `-3`).
* **Soundness is intact:** the ill-typed term is rejected during elaboration.
* **Two-line prototype fix:** use `groundInt?` (`patch/followup-hmod-groundInt.patch`, variant
  `omega_gi`).
  - **Verified:** the repro passes, and all 8 goals in `repro/hmod_followup_cases.lean` close; each
    of them fails on builtin, B, E and L.
  - The correctness tests pass, and the core suites give identical output.
  - The first two `limits.lean` goals become provable. `run.sh` expects exactly those two
    `fail_if_success` trips.
* Lean's own tests contain no negative or computed `Int` modulus.

This is a **bug report** with a two-line fix, independent of the `k = 0` work. It may suit a first
issue better than the performance change. Draft: `ISSUE-hmod.md`. The project's rule is one
contribution at a time, so the choice of which to file first is yours.
